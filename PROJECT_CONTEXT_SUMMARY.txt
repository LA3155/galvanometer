GD32F303 智能穿戴功耗分析仪项目上下文总结
更新时间：2026-08-14

一、项目定位

本项目是基于 GD32F303CGT6 的智能穿戴设备功耗分析仪，目标是给手表等低功耗设备供电，同时测量 DUT 端电压、电流、功耗，并在 ST7789 屏幕上实时显示和绘制曲线；后续通过 USB CDC 导出快照 CSV 和全量日志，用于功耗分析、简历展示和秋招项目讲解。

项目核心不是单纯电流表，而是“面向低功耗设备的功耗分析工具”：
- DUT 供电控制
- INA226 高边采样
- 10mΩ / 1Ω / 10Ω 三档手动量程
- ST7789 实时显示
- 100Hz 采样
- 环形缓冲区快照
- USB CDC 导出 CSV
- 后续 SPI Flash 日志记录

- I2C 能读到 INA226 ID 0x2260，INA226 工作正常。
- INA226 三档采样电阻已通过已知电阻负载验证，基础测量链路可用。
- USB CDC 现在能枚举成 COM 口，并能发送 HELLO、CSV 文本。

硬件注意：
- 板子 USB D+ 原设计缺少 1.5k 上拉，后续用户临时焊接 1k 上拉到 3V3，使 PC 可以识别 USB CDC。该方案可用于短时间调试，但不是严谨量产方案。
- Type-C 母座同时负责供电和 USB CDC 通信。
- ST-LINK 的 3.3V 脚主要是目标电压检测，板子实际供电仍由 Type-C 提供。
- Type-C 公头输出是专用 DUT 输出，不是标准 USB-C 5V 输出，应避免误插普通设备。

三、硬件量程和测量结果

INA226 shunt voltage 寄存器 0x01 的 LSB 是 2.5uV。

电流计算：
- Vshunt_uV = shunt_raw * 2.5uV
- I = Vshunt / Rshunt

三档换算：
- 10Ω 档：I_uA = shunt_uV / 10
- 1Ω 档：I_uA = shunt_uV
- 10mΩ 档：I_uA = shunt_uV * 100

Bus voltage：
- 0x02 寄存器，LSB = 1.25mV
- bus_mV = bus_raw * 1.25mV

功耗：
- power_uW = bus_mV * current_uA / 1000

用户实测记录：
1. 10Ω 档
   - 1kΩ 负载：约 3.274mA
   - 2kΩ 负载：0x01 = 6599，约 1.64975mA

2. 1Ω 档
   - 330Ω 负载：0x01 = 3981，约 9.9525mA
   - 100Ω 负载：0x01 = 12997，约 32.4925mA

3. 10mΩ 档
   - 100Ω 负载：0x01 = 128，约 32mA
   - 33Ω 负载：0x01 = 385，约 96.25mA

手表实测，10mΩ 全程测量：
- 亮屏：约 80mA，约 270mW
- 亮度下降：约 55mA，约 180mW
- 黑屏：约 1~2mA，约 5mW

量程取舍：
- 10mΩ 档适合启动、亮屏、大电流，全程不断电最稳，但低电流分辨率差。
- 10Ω 档适合睡眠小电流，但不适合让手表经历启动/亮屏大电流，会产生明显压降。
- 当前用户不想热拔插和断电切档，所以先接受 10mΩ 全程测量，用于状态趋势分析。

五、当前代码结构和已知问题

1. CDC 发送分包

cdc_printf 的格式化缓冲区已改到 256，但 USB CDC 单包仍约 64 字节。cdc_write 不能直接截断长数据，应循环分包发送。

建议 cdc_write 逻辑：
- 判断 USBD_CONFIGURED
- 获取 usb_cdc_handler
- while(sent < len)
  - 等待 cdc_acm_check_ready() 就绪
  - chunk = min(剩余长度, USB_CDC_RX_LEN)
  - memcpy 到 cdc->data
  - 设置 cdc->receive_length
  - cdc_acm_data_send
  - sent += chunk

否则长表头和长 CSV 行会被截断，出现“表头和第一行粘在一起”的现象。

2. KEY3 保存失败

PC 工具弹窗：

原因不是 MCU，而是 PC 文件无法写入：

解决：

- 换新文件名，如 power_log_001.csv
- 避免保存到被保护或同步占用的目录

3. 采样时间不稳定

用户导出的时间列出现 10、50、100、160、210...，不是严格 10ms。主要原因：
- 采样、LCD 数值刷新、波形绘制、按键处理都在同一个 10ms 分支中
- LCD 绘制和 I2C 读取会阻塞
- 如果 CDC 导出在运行中执行，也会进一步阻塞

建议结构：
- 使用硬件定时器产生 100Hz 节拍
- 定时器中断只置位 g_sample_10ms_flag，不读 I2C、不刷屏、不发送 CDC
- 主循环检测 flag 后执行 INA226 读取和缓冲区写入
- LCD 数值显示降低到 20Hz 或 10Hz
- 波形绘制可以每个样本画一点，但要优化为只清一列再画点
- CSV 导出建议暂停采样或使用导出状态机分批发送

4. 主循环调度建议

不要让 10ms 和 50ms 共用同一个 last_sample_ms。

推荐：
static uint32_t last_sample_ms = 0;
static uint32_t last_ui_ms = 0;

if(now - last_sample_ms >= 10) {
    last_sample_ms += 10;
    ina226_read_sample(...);
    waveform_push(...);
}

if(now - last_ui_ms >= 50) {
    last_ui_ms += 50;
    lcd_show_power_sample(...);
}

更专业的下一步是改为 TIMER2 100Hz 中断置标志。

七、环形缓冲区设计思路

用户希望：
- 日常运行时把采样数据放入 200 点环形缓冲区
- KEY3 导出当前屏幕/当前 200 点快照
- 后续每满 200 点写一次 SPI Flash，用于 KEY4 导出全量数据

建议设计：
- 采样频率 100Hz，200 点约 2 秒
- KEY3：导出 RAM 环形缓冲区中的最近 200 点 CSV
- KEY4：导出 Flash 中从启动到当前的完整日志

注意：
- 如果只在 200 点满时写 Flash，突然断电会丢失当前未满的最多 2 秒数据
- 改进方法：保留 RAM 当前缓冲区，导出全量时先导出 Flash 已写块，再导出 RAM 未写入部分
- 后续可加入块头、序号、CRC、range、flags

当前 log_record_t 结构偏“200 点快照”，后续如果做 Flash 日志，建议拆成单条记录结构：

typedef struct {
    uint32_t time_ms;
    uint16_t bus_mV;
    int32_t current_uA;
    int32_t power_uW;
    uint8_t range;
    uint8_t flags;
    uint16_t crc;
} log_record_item_t;

flags 可表示：过流、量程变化、按键快照、触发事件等。
crc 用于后续检查 Flash 数据完整性。
